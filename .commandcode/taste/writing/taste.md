# Writing & Documentation

- Always applies these style rules to docs and blog posts: sentence case for headings, hyphen "-" instead of em dash "—", straight quotes instead of curly quotes, no "---" horizontal rules, bold/italic for emphasis, and internal links where needed. Confidence: 1.0
- Writes documentation as tutorials that explain why a feature is needed and its concrete benefits, with setup instructions both via builder and via code, aimed at technical and non-technical users alike. Confidence: 0.9
- Prefers concise, scannable docs; trims long sections and reduces the number of options/links that overwhelm readers. Confidence: 0.9
- When asked to rewrite a docs page to be "better and easier to understand", improves readability from the reader's perspective: a one-line intro describing what each group/section is for, a clear distinction between integration types (official support vs MB extension) so readers know what action to take, and dash separators for scanning. Confidence: 0.7
- Preserves the user's curated content lists (e.g., plugins/themes/hostings that the user has added or removed) when rewriting docs; improves presentation and structure only, not the substance of the lists. Confidence: 0.6
- Checks technical docs for grammar, spelling, and natural phrasing for American English readers. Confidence: 0.9
- Avoids wording that makes a feature sound overly limited or restrictive (e.g., "few post field values", "best for simple, in-editor use cases"); frames scope so users don't feel boxed in. Confidence: 0.8
- Frames product compatibility positively: avoids intro wording that implies plugins/themes may have problems or need "extra work" to run together; instead emphasizes tested/confirmed compatibility and that the product works seamlessly with most plugins and themes. Confidence: 0.8
- Frames curated provider lists (e.g., hostings) as a non-endorsement option, not a recommendation: after stating the product works on all providers/hosts, introduces the list with a conditional "if you need..." framing (e.g., "If you need a powerful host that is optimized for developers, you can consider the following providers:"); avoids imperative "use..." wording, plain "compatible with" / "also works well with" phrasings, and anything boastful ("ko phô trương"), since the company does not endorse or test specific hosts.
